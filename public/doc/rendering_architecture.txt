============================================================
PixiJS 数据驱动渲染引擎架构设计方案
============================================================

1. 核心理念
-----------
采用“逻辑与渲染完全解耦”的架构。游戏逻辑层只负责计算状态，渲染层只负责根据指令绘图。
通过一套自定义的 DSL (Domain Specific Language) 脚本实现录像保存、回放和视频导出。

2. 数据流向
-----------
实时游戏：逻辑模拟 -> 结构化数据 (内存) -> PixiJS 渲染器
录像保存：结构化数据 -> DSL 转换模块 -> .txt 脚本文件
录像回放：.txt 脚本文件 -> DSL 转换模块 -> 结构化数据 -> PixiJS 渲染器
视频导出：Remotion -> 读取 .txt 脚本 -> PixiJS 渲染器 -> MP4

3. 脚本规范 (DSL)
-----------------
采用平铺式指令流，易于人类阅读和流式解析。
示例：
[FRAME 0]
<BALL id=1 x=100.5 y=200.0 r=20 c=#ff0000>
<SPRITE id=hero src="hero.png" x=500 y=300>
[FRAME 1]
<BALL id=1 x=102.5 y=201.0>

* 关键点：每一帧记录的是“绝对位置”，支持随机跳帧访问，防止误差累积。

4. 渲染层优化策略
-----------------
- 扁平化渲染：放弃复杂的 Container 嵌套，逻辑层直接计算绝对坐标。
- 对象池 (Object Pooling)：不重复创建/销毁精灵，根据 ID 复用已有的 Pixi 对象。
- 粒子容器 (ParticleContainer)：对于成千上万个重复图片（如弹幕），自动切换至粒子容器以获取 GPU 加速。
- 滤镜 (Filters)：作为可选属性附加在对象指令中，由渲染器统一处理。

5. 性能考量
-----------
- 优先使用 JSON 或结构化数据进行实时渲染。
- DSL 脚本仅用于持久化存储（录像）和跨平台交换。
- 追求“傻瓜式渲染器”原则：渲染器不带逻辑，只负责执行当前帧的数值赋值。

6. 后续扩展
-----------
- 二进制格式支持：若录像文件过大，可引入 TypedArrays (ArrayBuffer) 存储。
- 宏指令：支持自定义复杂图形的简写指令。

7. 音频管理策略 (Audio Management)
----------------------------------
- DSL 指令化：音频触发同样作为指令记录在 DSL 中。
  示例：<SOUND id=s1 src="boom.mp3" priority=10 vol=0.8>
- 浏览器适配：针对 Web Audio API 环境，采取极度保守的资源管理。
- 存在物理声道上限 (Physical Voice Limit)：强制限制在 8-12 个并发声道，防止浏览器内存溢出。
- 预解码对象池：常用音效预加载为 AudioBuffer，避免实时解码产生的 CPU 峰值。
- 音频节点池 (Audio Node Pooling)：
  * 预先创建固定数量的播放通道（SourceNode + GainNode 组合）。
  * 播放新声音时，直接复用闲置通道或抢占低优先级通道，仅替换 Buffer 数据。
  * 严禁在主循环中 new AudioContext 或频繁创建节点，将垃圾回收 (GC) 压力降至最低。
- 抢占式算法 (Preemption)：
  * 优先级排序：BGM(100) > 关键反馈(50) > 普通音效(10)。
  * 硬切断机制：当新高优先级声音进入时，立即 stop() 并重置最低优先级声道，不进行复杂的淡出计算以节省性能。
- 逻辑层过滤：
  * 距离过滤：超出视野范围的声音不进入 DSL。
  * 频率限制：同一 ID 的音效在极短时间内（如 50ms）不重复触发。
- Remotion 合成：导出时在 Node.js 环境下进行高质量多轨混音，不受浏览器声道限制。
